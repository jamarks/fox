# Remote Fox passkey (opt-in)

`FOX_PUBLIC_ORIGIN=https://fox.example.com` enables a second deployment mode. The default remains localhost-only. A remote process still listens only on 127.0.0.1; an HTTPS reverse proxy must preserve the configured public Host, terminate TLS, forward WebSocket upgrades and refuse HTTP access to Fox's loopback port from the network. Fox checks the configured Host and exact browser Origin for state-changing requests and terminal upgrades and issues Secure, HttpOnly, SameSite=Strict cookies. No X-Forwarded-* value is trusted for authorization.

Registration is not open to the internet. An administrator connected over SSH runs `node bin/fox-enroll.mjs` as the Fox service user, with the same HOME and FOX_PUBLIC_ORIGIN. The command creates an expiring, one-time random enrollment code (hashed on disk). Entering that code on the HTTPS login page authorizes registration options and binds the challenge to that code; successful registration saves the credential and consumes the code. No credentials means fail-closed unless a valid code has been issued. Credential records carry their RP ID, so moving the existing localhost passkey record to a remote domain fails at startup rather than silently resetting access; a remote deployment starts with its own separate HOME and passkey.

This prepares Fox for deployment, not a production rollout. DNS, TLS reverse proxy, firewall, SSH hardening, process supervision, account setup and real-browser passkey verification are separate steps. Do not enable a public proxy until those are verified. Do not share a storage directory between Fox on localhost and a remote domain.
